3. REST e suas restrições ↑ conteúdo

REST é um estilo arquitetural definido por Roy Fielding na sua tese de doutorado, em 2000. Um estilo arquitetural não é uma biblioteca nem um protocolo: é um conjunto de restrições. Quem respeita as restrições ganha certas propriedades, como escalabilidade e independência entre cliente e servidor. Uma API RESTful é a que respeita essas restrições, e não simplesmente a que usa JSON.

RestriçãoO que exigeO que se ganha
Cliente-servidorInterface e dados separados por uma API.Cada lado evolui sozinho.
Sem estadoCada requisição traz tudo de que precisa, inclusive a credencial (no ServiceHub, o token).Qualquer instância atende qualquer requisição.
CacheA resposta diz se pode ser guardada e por quanto tempo.Menos idas ao servidor.
Interface uniformeRecursos identificados por URI, manipulados por representações, com métodos e status padronizados.Quem conhece HTTP já sabe usar a API.
Sistema em camadasO cliente não sabe se fala com o servidor final ou com um intermediário.Balanceador, proxy e gateway no meio, sem mudar o cliente.
Código sob demandaOpcional: o servidor envia código executável.Raramente usada em APIs.

A restrição mais cobrada: sem estado

Imagine uma loja virtual com duas instâncias da API atrás de um balanceador. Se a instância A guarda na memória "o usuário 7 está logado", a próxima requisição desse usuário pode cair na instância B, que não sabe de nada e o trata como desconhecido. A saída é cada requisição carregar a própria prova de identidade. No ServiceHub, essa prova é o token JWT enviado no cabeçalho Authorization (tema da Semana 09).

Confusão comum

"Usa HTTP e JSON, então é REST." Uma API com POST /getUser ou GET /deleteService?id=3 usa HTTP só como transporte: o verbo está na URI e o método perdeu o significado. Isso quebra a interface uniforme.

URIs: substantivos, não verbos

A URI identifica o recurso; o método diz a ação. Coleções vão no plural, em minúsculas, com hífen entre palavras (/service-requests); o identificador vem depois da coleção (/services/12); filtros, ordenação e paginação vão na query string; a versão aparece no caminho desde o primeiro endpoint (/api/v1). Uma mudança de estado específica, como a da ordem, vira um sub-recurso: PATCH /api/v1/service-requests/31/status.

4. Semântica HTTP: métodos e status ↑ conteúdo

Uma mensagem HTTP tem três partes que dizem coisas diferentes. O método diz a intenção; o status code diz o resultado; os cabeçalhos dizem o formato e os metadados. Dois cabeçalhos aparecem em quase toda prova: Content-Type descreve o corpo que está sendo enviado, e Accept pede o formato da resposta.

Requisição

POST /api/v1/services HTTP/1.1
Content-Type: application/json
Accept: application/json

{ "title": "Pintura", ... }

Resposta

HTTP/1.1 201 Created
Location: /api/v1/services/12
Content-Type: application/json

{ "id": 12, "title": "Pintura", ... }

Métodos: seguro e idempotente

Um método é seguro quando não altera o estado do servidor. É idempotente quando repetir a mesma chamada deixa o servidor no mesmo estado que uma chamada só, mesmo que a resposta mude. Essas propriedades importam porque clientes, proxies e bibliotecas repetem requisições automaticamente quando a rede falha: repetir um GET ou um PUT é inofensivo; repetir um POST pode criar dois registros.

MétodoExemplo no ServiceHubSeguroIdempotente
GETGET /api/v1/services?page=0&size=20SimSim
POSTPOST /api/v1/services → 201 + LocationNãoNão
PUTPUT /api/v1/services/12 (substitui a representação)NãoSim
PATCHPATCH /api/v1/service-requests/31/statusNãoNão garantido
DELETEDELETE /api/v1/services/12 → 204NãoSim
Pergunta clássica

O segundo DELETE do mesmo serviço é idempotente mesmo respondendo diferente da primeira vez? Sim. Idempotência fala do estado final do servidor, e não da resposta. No ServiceHub o DELETE é exclusão lógica (ADR-0002): o registro continua no banco com active=false, e o estado final é o mesmo depois de uma ou de várias chamadas.

Status: cada cenário tem um só

As famílias de status respondem "de quem é a culpa". 2xx é sucesso. 3xx é redirecionamento. 4xx é erro do cliente: ele pode corrigir o pedido e tentar de novo. 5xx é erro do servidor e nunca é uma resposta planejada: um 500 significa que faltou tratar um caso.

Cenário no ServiceHubResposta
Serviço criado201 Created + Location
Listagem de serviços200 OK, página com content
Serviço desativado (exclusão lógica)204 No Content
Preço ausente no corpo400 com errors[]
GET /api/v1/services/999404 Not Found
E-mail já cadastrado (RN01)409 Conflict
Ordem COMPLETED volta para ACCEPTED409 invalid-transition
Corpo enviado como text/plain415 Unsupported Media Type
A confusão mais comum da prova: 400 × 409

400 diz que o pedido está malformado: falta campo, o tipo está errado, o valor está fora do formato. 409 diz que o pedido é válido, mas conflita com o estado atual do recurso: o e-mail já existe, a transição não é permitida a partir do status atual. Teste mental: "se o banco estivesse vazio, este pedido daria certo?" Se sim, o problema é de estado, e a resposta é 409.

Dois status voltam com força na Semana 08: 401 significa "não sei quem você é" (falta autenticação ou o token é inválido); 403 significa "sei quem você é, e você não pode fazer isto".

5. O domínio: a máquina de estados da ordem ↑ conteúdo

Uma máquina de estados descreve os estados possíveis de um objeto e as transições permitidas entre eles. Ela aparece em qualquer domínio com um processo: um pedido de compra (aguardando pagamento, pago, enviado, entregue), uma matrícula, um chamado de suporte. Modelar o processo como máquina de estados torna explícito o que é proibido, e o proibido vira regra testável.

A tabela de transições produz dois erros diferentes, e essa distinção cai em prova:

SituaçãoStatusPor quê
COMPLETED → ACCEPTED, pedido por qualquer um409A transição não existe na tabela, para ninguém. É conflito com o estado atual.
PENDING → ACCEPTED, pedido pelo cliente403A transição existe, mas não pertence ao papel de quem pediu.
O que a IA não sabe sozinha

As regras vêm do Mapa, não do código gerado. Um assistente que nunca leu a seção 4 do Mapa vai inventar uma tabela plausível, por exemplo deixando o cliente concluir a ordem. A tabela de transições é o tipo de conhecimento de domínio que só a equipe pode especificar.

6. IoC, injeção de dependência e camadas ↑ conteúdo

Os termos

  • Inversão de controle (IoC): quem cria e liga os objetos é o framework, e não o seu código. Você declara as peças; o contêiner monta o sistema.
  • Injeção de dependência (DI): a dependência chega de fora, de preferência pelo construtor.
  • Bean: objeto criado e gerenciado pelo contêiner do Spring.

Por que isso existe: uma classe que faz new RepositorioPostgres() por dentro fica presa àquela implementação. Uma classe que recebe o repositório pelo construtor depende só de um tipo, e o teste pode entregar um dublê no lugar do repositório real. No ServiceHub, os serviços recebem todas as dependências no construtor:

@Service
@Transactional
public class ServiceRequestService {
    private final ServiceRequestRepository requestRepository;
    private final CurrentUser currentUser;
    // ... mais três dependências, todas recebidas no construtor (resumido)
}

Injeção no campo

@Autowired
private ServicoRepository repo;

O campo não pode ser final, a dependência fica escondida e o teste sem Spring precisa de reflexão para preencher o campo.

Injeção pelo construtor

private final ServicoRepository repo;
ServicoService(ServicoRepository repo) {
  this.repo = repo;
}

Campos final, dependências explícitas na assinatura e teste com um simples new ServicoService(dubleDoRepo).

Camadas: cada uma tem um papel e um limite

CamadaAnotaçõesFazNunca
Controller@RestController, @ValidRota, DTO, status codeRegra de negócio
Service@Service, @TransactionalRegras RN, monta o DTO de respostaDevolver entidade JPA
RepositoryJpaRepositoryConsultas parametrizadasDecidir regra
Entidade@Entity, @TableEspelha a tabelaSair na resposta HTTP

Pergunta típica: onde fica a regra "ninguém contrata o próprio serviço" (RN06)? No Service. Ela precisa do usuário atual e de dados do banco, e precisa valer para qualquer chamador, seja um controller, um teste ou uma tarefa agendada. Se estivesse no controller, outro ponto de entrada poderia pular a regra.

Para lembrar

Com spring.jpa.open-in-view=false, a sessão do banco fecha quando o método do Service termina. Por isso o DTO de resposta é montado dentro do método @Transactional do Service, e não no controller.

7. ORM e o ciclo de vida da entidade ↑ conteúdo

ORM (Object-Relational Mapping, mapeamento objeto-relacional) traduz entre o modelo de objetos do Java e o modelo relacional do banco. Os dois modelos pensam de forma diferente: objetos têm herança, identidade por referência e navegação de um objeto a outro; tabelas têm linhas, chaves e junções. Essa diferença tem nome, incompatibilidade de impedância objeto-relacional, e é o problema que o ORM resolve. Sem ele, cada consulta é SQL escrito à mão e cada linha é convertida em objeto campo a campo.

JPA (Jakarta Persistence) é a especificação, o contrato. Hibernate é a implementação que o Spring Boot usa. São coisas diferentes, como uma interface Java e a classe que a implementa.

No JavaNo bancoNo ServiceHub
Classe @EntityTabelaServiceOffering ↔ services
AtributoColunaprice ↔ price NUMERIC
ObjetoLinhaUm serviço publicado
Referência a outro objetoChave estrangeiraprovider ↔ provider_id
EnumTexto, com ou sem CHECK@Enumerated(STRING) ↔ VARCHAR
O custo do ORM

Navegar por referências sem cuidado gera o problema N+1: uma consulta para trazer N serviços e mais uma consulta por serviço para trazer o prestador de cada um. A ferramenta esconde o SQL, mas não o elimina.

Os quatro estados de uma entidade

O contexto de persistência é o "caderno" em que o Hibernate anota as entidades managed. No commit, ele compara cada entidade com o que leu do banco; o que mudou vira UPDATE. Esse mecanismo se chama dirty checking. Consequência prática: uma entidade managed alterada por um setter é gravada no commit mesmo sem chamar save. Fora da transação, a mesma alteração fica só no objeto em memória e se perde.

No ServiceHub a exclusão é lógica, então o fluxo real de um DELETE é: managed → setActive(false) → UPDATE no commit. E, com open-in-view=false, acessar uma associação lazy numa entidade detached lança LazyInitializationException.

8. Transações ↑ conteúdo

Uma transação agrupa operações no banco para que todas aconteçam ou nenhuma aconteça. O exemplo clássico é a transferência bancária: debitar de uma conta e creditar na outra. Se o sistema cair entre as duas operações, o dinheiro não pode sumir. As garantias de uma transação formam a sigla ACID:

GarantiaSignificado
AtomicidadeFalhou uma parte, desfaz-se tudo.
ConsistênciaAs restrições do banco (NOT NULL, CHECK, FK) valem ao fim da transação.
IsolamentoTransações simultâneas não enxergam o trabalho pela metade uma da outra.
DurabilidadeO que foi confirmado não se perde, mesmo com queda do servidor.

No ServiceHub, desativar um usuário também desativa os serviços dele (RN11). Se a segunda parte falhar, a primeira precisa ser desfeita: isso é atomicidade.

@TransactionalComportamento padrão no Spring
Onde colocarNo Service, onde a regra de negócio começa e termina. A unidade de trabalho é a regra, que pode tocar vários repositórios.
RollbackEm exceções não verificadas (RuntimeException e Error). Exceções verificadas não desfazem a transação, a menos que se configure rollbackFor.
readOnly = truePara consultas: avisa que não haverá escrita e dispensa o dirty checking.
Pegadinha

@Transactional funciona por meio de um proxy que o Spring coloca em volta do bean. Uma chamada de um método para outro dentro da mesma classe não passa pelo proxy, então a anotação do segundo método é ignorada.

9. Migrações com Flyway ↑ conteúdo

Uma migração é um script versionado que leva o schema do banco de uma versão para a próxima. A ideia vale para qualquer linguagem: o schema passa a ser código, guardado no Git, aplicado na mesma ordem em todas as máquinas. Sem migrações, cada colega tem um banco ligeiramente diferente, e o erro aparece só no ambiente de outra pessoa.

O Flyway aplica os arquivos V1__descricao.sql, V2__... em ordem e registra cada um numa tabela de histórico, com um checksum (uma soma de verificação do conteúdo). No ServiceHub, o Flyway escreve o schema e o Hibernate só confere:

-- V5__Create_service_requests_table.sql (resumido)
CREATE TABLE service_requests (
    id           BIGSERIAL PRIMARY KEY,
    service_id   BIGINT NOT NULL REFERENCES services(id),
    client_id    BIGINT NOT NULL REFERENCES users(id),
    status       VARCHAR(30) NOT NULL DEFAULT 'PENDING',
    total_price  NUMERIC(10,2) NOT NULL,
    CONSTRAINT chk_status CHECK (status IN
        ('PENDING','ACCEPTED','IN_PROGRESS','COMPLETED','CANCELLED'))
);
# application.properties
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
RegraPor quê
Toda mudança de entidade vem com uma nova migraçãoCom validate, o Hibernate não cria nem altera nada: se faltar coluna, a aplicação não sobe, e o erro diz qual.
Migração aplicada nunca é editadaO checksum muda e o Flyway recusa iniciar. Corrige-se com uma nova versão; no projeto de referência, a V6 removeu um índice redundante criado antes.
CHECK no banco mesmo com enum no JavaO banco é a última linha de defesa contra qualquer cliente que escreva nele: um script, outro sistema, uma migração futura.

10. Por que não H2: Postgres, Flyway e Testcontainers ↑ conteúdo

O H2 é um banco em memória escrito em Java, muito usado em tutoriais porque dispensa instalação. O problema é que ele fala outro dialeto de SQL. As migrações do ServiceHub usam recursos do PostgreSQL, como BIGSERIAL, NUMERIC(10,2), CHECK (status IN (...)) e ALTER TABLE ... DROP CONSTRAINT. Com H2, ou o Flyway falha, ou é preciso desligá-lo e usar ddl-auto=create-drop, e aí o teste roda contra um schema que não existe em produção.

CritérioH2 em memóriaPostgres 16 + Flyway
MigraçõesOutro dialeto: tipos, CHECK e ALTER podem falhar ou se comportar diferenteAs mesmas V1…Vn de produção
SchemaTentação de create-drop ou updateddl-auto=validate
Erro de SQLAparece no deployAparece no teste
Nos testes"Zero configuração"Testcontainers com postgres:16-alpine

O Testcontainers é uma biblioteca que, durante o teste, sobe um container Docker real e o descarta no fim. No ServiceHub, uma classe de configuração entrega o container ao Spring, e a anotação @ServiceConnection preenche URL, usuário e senha do datasource. O Flyway então aplica as mesmas migrações de produção a cada execução:

@TestConfiguration(proxyBeanMethods = false)
public class TestcontainersConfiguration {
    @Bean
    @ServiceConnection
    PostgreSQLContainer postgresContainer() {
        return new PostgreSQLContainer("postgres:16-alpine");
    }
}

O preço é ter o Docker ligado ao rodar os testes. A decisão e as consequências estão registradas no ADR-0005 do projeto de referência (docs/adr/0005-testcontainers-em-vez-de-h2.md). Os testes de integração com banco são tema da Semana 10; por ora, basta saber justificar a escolha.

11. DTO, ProblemDetail e OpenAPI ↑ conteúdo

DTO: a forma dos dados na fronteira

DTO (Data Transfer Object) é um objeto simples, sem regra, que carrega dados entre camadas ou sistemas. Martin Fowler descreve o padrão no catálogo de padrões de aplicações corporativas. Numa API, o DTO é o corpo que entra e o corpo que sai.

AspectoEntidadeDTO
RepresentaUma linha da tabelaUm caso de uso da API
Muda quandoO banco mudaO contrato muda
CamposTodos, inclusive passwordHashSó os que o cliente pode ver ou enviar
ValidaçãoRestrições do bancoBean Validation (@NotBlank, @Size)

O DTO evita dois riscos: vazar dados internos na resposta e aceitar campos que o cliente não deveria definir, problema conhecido como mass assignment e aprofundado na Semana 08. No ServiceHub, o DTO de criação de ordem não tem clientId, status nem preço; a API define os três:

@Schema(description = "Abertura de ordem de serviço. Cliente, status e preço são definidos pela API.")
public record ServiceRequestCreateDTO(
        @NotNull(message = "O serviço é obrigatório") @Positive Long serviceId,
        @Future(message = "A data agendada deve estar no futuro") LocalDateTime scheduledAt,
        @Size(max = 1000) String notes) { }   // resumido

ProblemDetail: todo erro no mesmo formato

A RFC 9457 (Problem Details for HTTP APIs) define um formato JSON padrão para erros, com o tipo de mídia application/problem+json. O Spring tem suporte nativo pela classe ProblemDetail. O campo type é o identificador estável do erro: o cliente da API programa contra ele, e não contra o texto de detail, que pode mudar.

Resposta 400

{
  "type": "urn:servicehub:problem:validation-error",
  "title": "Dados inválidos",
  "status": 400,
  "detail": "Um ou mais campos estão inválidos.",
  "instance": "/api/v1/services",
  "errors": [
    { "field": "price",
      "message": "O preço é obrigatório" }
  ]
}

Um ponto central de tradução

O GlobalExceptionHandler, anotado com @RestControllerAdvice, converte:

  • ResourceNotFoundException → 404
  • EmailAlreadyExistsException → 409
  • BusinessRuleException → 409
  • falha de @Valid → 400 com errors
  • qualquer outra → 500, sem stack trace
Erro comum em código gerado por IA

Lançar RuntimeException("preço inválido") para uma entrada errada. Ninguém trata essa exceção genérica, e o cliente recebe um 500 em vez de um 400 com o campo apontado.

OpenAPI: o contrato que se lê sem abrir o código

A OpenAPI é uma especificação para descrever APIs HTTP num documento JSON ou YAML: rotas, parâmetros, corpos, respostas e schemas. O Springdoc gera esse documento a partir do código; a linha 3.0.x é a que funciona com o Spring Boot 4. No projeto de referência, a interface Swagger UI fica em /docs e o documento em /api-docs/v1.

AnotaçãoUso bem feito
@Tag, @OperationUm summary que diz o que a rota faz no domínio ("Abrir ordem de serviço"), nunca "update resource".
@ApiResponseUm por status possível; os de erro com o schema ProblemDetail.
@Schema nos DTOsExemplos reais ("Instalação elétrica residencial"), não "string".

Uma confusão frequente: no documento OpenAPI, o campo openapi é a versão da especificação usada; o campo info.version é a versão do seu contrato. Teste rápido de qualidade: alguém de fora consegue chamar a rota certa só lendo o Swagger?

13. O checkpoint: o que precisa estar no repositório ↑ conteúdo

No checkpoint vale o repositório, não a promessa. A avaliação parte do commit marcado pela tag etapa-2: o que não está nesse commit não foi entregue, mesmo que funcione na máquina de alguém. O checkpoint não é formalidade; é a chance de receber devolutiva antes da entrega final.

A entrega é uma tag anotada

Uma tag é um nome fixo apontado para um commit. A tag anotada (git tag -a) é um objeto próprio no Git, com autor, data e mensagem; a tag leve é só um apelido. Para uma entrega, use a anotada: ela registra quem marcou e quando. Depois de marcar, a main continua evoluindo, e a avaliação olha exatamente o commit marcado.

git tag -a etapa-2 -m "Etapa 2: checkpoint da 1ª VA"
git push origin etapa-2

# teste final, em outra pasta
git clone <url-do-repo> conferencia
cd conferencia
git checkout etapa-2
./mvnw verify          # no Windows: mvnw.cmd verify

O clone limpo pega o clássico "na minha máquina funciona": um arquivo que nunca foi commitado, um segredo que só existe no seu .env, uma migração editada depois de aplicada no seu banco local. Se o verify passa numa pasta recém-clonada, com o Docker ligado, a entrega é reprodutível.

Antes de marcar

  • O README diz como subir o Postgres e a API.
  • Nenhum segredo commitado: .env está no .gitignore.
  • Nenhuma migração já aplicada foi editada.
  • ./mvnw verify passa num clone limpo.
  • git show etapa-2 --stat mostra o commit esperado.

Roteiro da apresentação: 8 a 10 minutos

  1. Contexto: domínio, papéis e a jornada do cliente e do prestador.
  2. Swagger: rotas e erros documentados.
  3. Ao vivo: uma chamada que dá 201, uma que dá 400 e uma que dá 404.
  4. Código: uma classe de cada camada.
  5. Decisão: um ADR, com problema, decisão e efeito. É a parte que a IA não faz pela equipe.
Logística

Suba o banco e a API antes de começar. Erro de compilação ao vivo consome o tempo da equipe. Cada integrante deve conseguir falar de pelo menos uma etapa do roteiro.

15. Glossário ↑ conteúdo

Restrição REST
Regra do estilo arquitetural de Fielding, como "sem estado" ou "interface uniforme".
Idempotente
Operação que, repetida, deixa o servidor no mesmo estado que uma execução só.
Método seguro
Método HTTP que não altera o estado do servidor, como GET.
Máquina de estados
Modelo com estados possíveis e transições permitidas entre eles.
IoC
Inversão de controle: o framework cria e liga os objetos.
ORM
Mapeamento entre objetos do programa e tabelas do banco relacional.
Contexto de persistência
Conjunto de entidades managed que o Hibernate acompanha numa transação.
Dirty checking
Detecção automática de alterações em entidades managed, gravadas no commit.
ACID
Atomicidade, consistência, isolamento e durabilidade: garantias de uma transação.
Rollback
Desfazer todas as operações de uma transação que falhou.
Migração
Script versionado que leva o schema de uma versão à próxima.
Checksum
Soma de verificação do conteúdo de um arquivo; detecta edição.
Testcontainers
Biblioteca que sobe containers Docker reais durante os testes.
DTO
Objeto sem regra que carrega dados na fronteira da API.
ProblemDetail
Formato padrão de erro em JSON definido pela RFC 9457.
Tag anotada
Marca do Git com autor, data e mensagem, apontada para um commit.
