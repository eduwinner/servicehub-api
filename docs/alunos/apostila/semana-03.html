2. Biblioteca ou framework ↑ conteúdo

Uma biblioteca é código que você chama quando precisa. Um framework é uma estrutura pronta que chama o seu código na hora certa. Essa troca de quem está no comando se chama inversão de controle (IoC, de Inversion of Control), resumida no lema "não nos chame, nós chamamos você".

AspectoBibliotecaFramework
Quem controla o fluxoO seu programaO framework
Como você usaChama uma função ou cria um objetoEscreve classes que ele encontra e executa
Exemplo genéricojava.time para calcular datasUm servidor web que chama o seu método a cada requisição
No ServiceHubJackson converte um objeto em JSONO Spring chama InfoController.info() em GET /api/v1/info

O código que chama info() não está no projeto: está no Spring MVC. O preço é aprender as convenções do framework; o ganho é não reescrever servidor, roteamento e conversão de JSON.

3. Anotações Java ↑ conteúdo

Uma anotação é um metadado preso a uma classe, método, campo ou parâmetro, escrito com @. Ela não muda o código por si só: alguém precisa lê-la. Pode ser o compilador, uma ferramenta de build ou o framework, em tempo de execução, por reflexão (a capacidade de um programa Java inspecionar as próprias classes enquanto roda).

Duas meta-anotações definem uma anotação nova: @Target diz onde ela pode ser usada, e @Retention diz até quando ela sobrevive.

RetençãoOnde a anotação existeExemplo
SOURCESó no código-fonte; o compilador descarta@Override
CLASSNo .class, mas não em execução (é o padrão)uso de ferramentas
RUNTIMEEm execução, lida por reflexão@RestController
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface Auditado {          // declara a anotação
    String valor() default "";
}

@Auditado(valor = "pedidos")         // usa a anotação
public class PedidoService { }

O Spring só enxerga @RestController, @Service ou @GetMapping porque elas têm retenção RUNTIME. Anotações também podem compor outras: @RestController é, ela mesma, anotada com @Controller e @ResponseBody.

4. Pacotes e visibilidade ↑ conteúdo

Um pacote agrupa classes relacionadas e cria um espaço de nomes: com.servicehub.controller.InfoController não se confunde com outra InfoController de outro pacote. Por convenção, o nome começa pelo domínio invertido da organização, em minúsculas. Junto com os modificadores de acesso, o pacote decide quem pode usar o quê:

ModificadorMesma classeMesmo pacoteSubclasse em outro pacoteQualquer lugar
privatesimnãonãonão
sem modificador (pacote)simsimnãonão
protectedsimsimsimnão
publicsimsimsimsim

Regra prática: comece pelo acesso mais restrito e abra só quando precisar. No ServiceHub, o conjunto SORTABLE de cada controller não tem modificador: só o pacote controller o enxerga.

Confusão comum

O pacote também importa para o Spring. A varredura de componentes começa no pacote da classe anotada com @SpringBootApplication e desce pelos subpacotes. Uma classe colocada fora dessa árvore, por exemplo em com.outra.coisa, simplesmente não é encontrada, e o endpoint responde 404 sem nenhum erro na inicialização.

5. Arquitetura em camadas ↑ conteúdo

Separar o sistema em camadas, cada uma com uma responsabilidade, permite trocar ou testar uma parte sem mexer nas outras. Fowler descreve três camadas principais: apresentação, domínio e fonte de dados. Exemplo genérico, uma loja virtual: a tela do carrinho é apresentação, a regra do frete é domínio, a tabela de pedidos é fonte de dados.

A regra da dependência diz que as setas só apontam num sentido. O service não conhece status codes; o repository não decide regra de negócio. Na Arquitetura Limpa, de Robert C. Martin, a ideia vai além: as dependências apontam para as regras de negócio, e o framework e o banco são detalhes.

Regra no controller

"Ninguém contrata o próprio serviço" escrita no controller. Quando surgir um segundo ponto de entrada (uma fila, uma tarefa agendada), a regra precisa ser copiada, e uma das cópias vai ficar para trás.

Regra no service

A regra mora no service. Qualquer ponto de entrada chama o mesmo método, e um teste de unidade verifica a regra sem subir HTTP.

6. O contêiner do Spring ↑ conteúdo

O Spring mantém um contêiner IoC, o ApplicationContext, que cria, liga e destrói objetos por você. Cada objeto gerenciado por ele se chama bean. É a inversão de controle aplicada à criação de objetos: você declara do que precisa; o contêiner decide quando e como criar.

Ciclo de vida de um bean

  1. Varredura: na subida, o Spring procura classes anotadas nos subpacotes da aplicação.
  2. Criação: chama o construtor e injeta as dependências, que também são beans.
  3. Inicialização: roda métodos anotados com @PostConstruct, se houver.
  4. Uso: o bean atende todas as requisições enquanto a aplicação está no ar.
  5. Destruição: no desligamento, roda métodos com @PreDestroy.
Confusão comum

Por padrão, o bean é singleton: uma única instância, compartilhada por todas as requisições ao mesmo tempo. Se dois clientes chamam o mesmo endpoint simultaneamente, existe um só InfoController. Por isso nunca se guarda dado de um usuário num campo do controller ou do service: outra requisição, em outra thread, pode ler ou sobrescrever.

Estereótipos: o papel de cada classe

Um estereótipo é uma anotação que transforma a classe em bean e declara a camada a que ela pertence. Todos derivam de @Component.

AnotaçãoCamadaO que acrescenta
@ComponentqualquerSó registra a classe como bean.
@ServicedomínioNada além do nome: documenta que ali mora regra de negócio.
@RepositorydadosTraduz exceções do banco para a hierarquia DataAccessException.
@RestControllerapresentação@Controller + @ResponseBody: o retorno do método vira o corpo da resposta, em JSON.
@Configuration + @BeanconfiguraçãoCria, por um método, beans de classes que não são suas.

Usar @Service em vez de @Component não muda o comportamento, mas comunica intenção para quem lê e para a IA. No ServiceHub, os repositories são interfaces que estendem JpaRepository: o Spring Data gera a implementação sozinho (Semana 04).

Injeção de dependências pelo construtor

Injeção de dependências é a classe receber de fora os objetos de que precisa, em vez de criá-los com new. Há três formas no Spring: pelo construtor, por setter e direto no campo. A recomendada é a primeira.

No campo

@Service
class PedidoService {
  @Autowired
  private PedidoRepository repo;
}

Funciona, mas esconde a dependência, impede o final e obriga a subir o Spring para testar. Erro comum em tutoriais e em código gerado por IA.

No construtor

@Service
class PedidoService {
  private final PedidoRepository repo;
  PedidoService(PedidoRepository repo) {
    this.repo = repo;
  }
}

O campo é final, o objeto nunca nasce incompleto, e o teste cria a classe com new, passando um dublê. Com um único construtor, @Autowired é dispensável. Muitas dependências no construtor sinalizam uma classe que faz coisas demais.

7. Configuração externa ↑ conteúdo

O Spring Boot segue o princípio de convenção sobre configuração: olha o que está no classpath e configura o resto com padrões sensatos. Colocou o starter de web? Sobe um Tomcat embutido na porta 8080, com JSON pronto. Quer outro valor? Sobrescreva no application.properties.

Mas o mesmo .jar roda no seu notebook, na integração contínua e em produção. O que muda entre esses ambientes (porta, endereço do banco, senhas) não pode estar compilado: fica em configuração externa, ideia que o guia The Twelve-Factor App chama de "configuração no ambiente". O padrão do Spring é ler uma variável de ambiente com um valor de desenvolvimento como reserva:

server.port=${SERVER_PORT:8080}
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5433/servicehub}
#            ${VARIAVEL:padrao} → usa a variável; se não existir, o padrão de dev
ConceitoComo funciona
PrecedênciaUma variável de ambiente vence o valor escrito no arquivo. SERVER_PORT=9090 sobe a API na 9090 sem recompilar.
Perfisapplication-prod.properties só vale quando o perfil prod está ativo, por exemplo com SPRING_PROFILES_ACTIVE=prod. Ele acrescenta ou sobrescreve valores do arquivo principal.
SegredosSenha e chave nunca entram no Git. O arquivo .env fica no .gitignore; um .env.example sem valores reais é versionado para documentar as variáveis.
Confusão comum

Dar padrão a um segredo, como ${JWT_SECRET:minhachave}, parece prático, mas, se alguém esquecer de definir a variável em produção, a aplicação sobe com a chave que está no Git. Para segredos, o padrão deve ser vazio, e a aplicação deve se recusar a subir sem eles.

8. Starters e o Initializr ↑ conteúdo

Um starter é uma dependência do Spring Boot que reúne a biblioteca de um recurso e a autoconfiguração dela. No Spring Boot 4, a autoconfiguração foi dividida em módulos por recurso, e cada recurso tem o seu starter:

RecursoStarter no pom.xmlSemana
Web (Spring MVC)spring-boot-starter-webmvc3
JPA e Hibernatespring-boot-starter-data-jpa4
Migraçõesspring-boot-starter-flyway4
Validaçãospring-boot-starter-validation4
Saúde e métricasspring-boot-starter-actuator4
Segurança e JWTspring-boot-starter-security, spring-boot-starter-oauth2-resource-server8 e 9

Só a biblioteca

<groupId>org.flywaydb</groupId>
<artifactId>flyway-core</artifactId>

A aplicação sobe, as migrações não rodam, e nenhum erro aparece.

Com o starter

<groupId>org.springframework.boot</groupId>
<artifactId>spring-boot-starter-flyway</artifactId>

A autoconfiguração entra junto e o Flyway roda na subida.

Regra para a vida toda do projeto: recurso que não ativa, sem log e sem erro? Procure primeiro o spring-boot-starter-* que está faltando.

O Spring Initializr (start.spring.io) gera o esqueleto do projeto: pom.xml, Maven Wrapper, classe principal e teste de contexto.

9. Git: controle de versão distribuído ↑ conteúdo

Um sistema de controle de versão guarda a história de cada mudança: quem fez, quando e por quê. No modelo centralizado, a história mora num servidor só, e quem está sem rede não registra nada. No modelo distribuído, como o Git, cada clone tem a história completa e funciona sem rede; a sincronização é feita depois.

ConceitoO que é
CommitUma fotografia do projeto, com autor, data, mensagem, um identificador (hash) e o commit anterior. A história é a corrente de commits.
BranchUm ponteiro móvel para um commit. Criar uma é barato: é uma linha de trabalho isolada, não uma cópia da pasta. O .gitignore lista o que nunca entra no repositório, como target/ e o .env.
MergeJunta duas histórias. Se os dois lados mudaram as mesmas linhas, há conflito, e uma pessoa decide o resultado.
RemotoOutra cópia do repositório, como o origin no GitHub. push envia commits; fetch e pull trazem.
TagUm nome fixo para um commit, como etapa-1. Diferente da branch, não se move.

10. GitHub Flow, commits e versões ↑ conteúdo

O GitHub Flow é um fluxo simples: a main está sempre funcionando; cada entrega nasce numa branch própria; a branch volta para a main por um pull request revisado.

Ninguém faz push direto na main: no GitHub, uma regra de proteção da branch pode exigir pull request e aprovação. Se a branch quebrou algo, a main continua de pé e o problema aparece na revisão. O pull request é o momento do movimento Revisar: um colega confere o código, inclusive o que a IA gerou, contra a especificação. Um bom pull request tem título no padrão de commits, explica o que muda e como testar, e só entra depois de aprovado.

Conventional Commits

A especificação Conventional Commits padroniza a mensagem: tipo: assunto, com um escopo opcional entre parênteses, como docs(alunos): .... O assunto é curto e diz o que muda; se precisar de mais, o corpo do commit explica o porquê. Na disciplina, as mensagens são em português.

TipoQuandoExemplo
featNova funcionalidadefeat: prefixo /api/v1, endpoint de info e filtro X-Request-Id
fixCorreção de bugfix: 404 em vez de 500 para serviço inexistente
testSó testestest: Testcontainers Postgres para os testes de contexto
docsSó documentaçãodocs: README, ADR-0001 e CLAUDE.md da fase 0
choreBuild e configuraçãochore: fixar Java 21

Versionamento semântico

No versionamento semântico (SemVer), a versão tem a forma MAIOR.MENOR.CORREÇÃO, e cada parte é uma promessa para quem usa a API:

  • MAIOR sobe numa mudança incompatível, em que o cliente precisa se adaptar (commit com BREAKING CHANGE ou feat!): 1.4.2 → 2.0.0.
  • MENOR sobe numa funcionalidade nova e compatível (feat): 1.4.2 → 1.5.0.
  • CORREÇÃO sobe numa correção compatível (fix): 1.4.2 → 1.4.3.

Numa API REST, remover um campo do JSON ou mudar o significado de um status é mudança MAIOR; é para isso que a rota carrega /v1, e uma quebra de contrato vira /v2. Versões 0.y.z indicam desenvolvimento inicial, em que tudo pode mudar. O 0.0.1-SNAPSHOT do pom.xml é isso, e SNAPSHOT é a convenção do Maven para versão em desenvolvimento.

Para lembrar

As tags da disciplina, etapa-1, etapa-2 e assim por diante, marcam entregas, não versões semânticas. Use tag anotada (git tag -a), que guarda autor, data e mensagem, criada na main depois do merge. Na banca, a equipe apresenta a partir de uma tag, não "do que estava na minha máquina".

11. Contexto para a IA e ADRs ↑ conteúdo

O assistente de IA começa cada sessão sem memória do projeto. O que não estiver escrito, ele chuta, normalmente com a versão mais comum na internet, que não é a nossa. Gerenciar esse contexto é trabalho de engenharia, e ele mora em dois documentos versionados no repositório.

CLAUDE.md ou AGENTS.md

É um arquivo Markdown na raiz do projeto com o que um assistente precisa saber antes de mexer no código. O CLAUDE.md é lido pelo Claude Code ao abrir o projeto; o AGENTS.md é uma convenção aberta, lida por outros assistentes de código. A equipe escolhe um nome e mantém um só. O conteúdo deve ser curto, verdadeiro e atualizado a cada bloco; cada "pegadinha" nasce de um erro real:

# ServiceHub API
## Stack
Java 21 · Spring Boot 4.x · Maven Wrapper
## Comandos
mvnw.cmd clean install · mvnw.cmd spring-boot:run
## Convenções
- Rotas em /api/v1; POST responde 201 + Location
- Pacotes em com.servicehub; DTOs novos são record
- Commits em Conventional Commits, em português
## Pegadinhas
- Boot 4: recurso novo pede spring-boot-starter-<recurso>
- @MockBean não existe mais: use @MockitoBean

ADR: registro de decisão de arquitetura

Um ADR (Architecture Decision Record) é um texto curto que registra uma decisão de arquitetura, o contexto em que ela foi tomada e o que ela custa. Resolve um problema comum: meses depois ninguém lembra por que o sistema é assim, e a discussão recomeça do zero. O formato proposto por Michael Nygard tem cinco partes:

SeçãoResponde
TítuloQual decisão, em poucas palavras, com número sequencial
StatusProposto, aceito ou substituído (por qual ADR)
ContextoQue problema e que forças existiam
DecisãoO que foi escolhido, na voz ativa: "usaremos..."
ConsequênciasO que melhora e o que piora, inclusive os custos

Escreva um ADR quando a escolha é cara de desfazer ou não é óbvia para quem chega. Um ADR nunca se apaga: se a equipe mudar de ideia, um ADR novo substitui o antigo, e a história fica. Para a IA, o ADR também é contexto: ela para de sugerir o que a equipe já descartou. Exemplo genérico, fora do ServiceHub:

# ADR-0003 — PostgreSQL em vez de banco de documentos
Status: aceito
## Contexto
Pedidos, clientes e produtos se relacionam e precisam de integridade
(um pedido não pode apontar para um cliente que não existe).
## Decisão
Usaremos PostgreSQL, com o schema versionado por migrações.
## Consequências
+ Chaves estrangeiras e transações garantem a integridade.
- Toda mudança de schema exige uma migração nova.

O primeiro endpoint

Resumido, sem imports e sem as anotações OpenAPI da Semana 05:

@RestController
@RequestMapping("/api/v1/info")
public class InfoController {
    private final String version;

    public InfoController(ObjectProvider<BuildProperties> buildProperties) {
        BuildProperties props = buildProperties.getIfAvailable();
        this.version = props != null ? props.getVersion() : "dev";
    }

    @GetMapping
    public InfoResponse info() {
        return new InfoResponse("OK", version, "ServiceHub API operacional");
    }
}

public record InfoResponse(String status, String version, String message) { }

Repare: injeção pelo construtor, rota versionada e um record como DTO, sem Lombok. Na sua primeira versão, a versão pode ser um texto fixo, como "0.0.1-SNAPSHOT". O application.properties usa ${VARIAVEL:padrao} como na seção 7, e o segredo do JWT tem padrão vazio: ${JWT_SECRET:}.

14. Glossário ↑ conteúdo

Framework
Estrutura pronta que chama o seu código na hora certa.
Inversão de controle
O framework, e não o seu programa, controla o fluxo e a criação de objetos.
Anotação
Metadado preso ao código, lido pelo compilador, por ferramentas ou pelo framework.
Reflexão
Capacidade de um programa inspecionar as próprias classes em execução.
Pacote
Agrupamento de classes que cria um espaço de nomes e limita a visibilidade.
Bean
Objeto criado e gerenciado pelo contêiner do Spring; singleton por padrão.
Estereótipo
Anotação que registra a classe como bean e indica sua camada.
Starter
Dependência do Boot que reúne a biblioteca e a autoconfiguração de um recurso.
Perfil
Conjunto de configurações ativado por ambiente, como prod.
Commit
Fotografia do projeto com autor, mensagem e ligação ao commit anterior.
Branch
Ponteiro móvel para um commit; uma linha de trabalho isolada.
Pull request
Pedido de revisão e merge de uma branch na main.
Tag anotada
Nome fixo para um commit, com autor, data e mensagem.
SemVer
Versão MAIOR.MENOR.CORREÇÃO, em que cada parte indica o tipo de mudança.
ADR
Registro curto de uma decisão de arquitetura: contexto, decisão, consequências.
