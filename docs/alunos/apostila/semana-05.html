1. Objetivos da semana ↑ conteúdo

Ao final desta semana você deve ser capaz de:

  1. explicar o que um contrato de API fixa e comparar as abordagens design-first e code-first;
  2. ler e escrever um documento OpenAPI com info, servers, paths, components, schemas e securitySchemes, usando JSON Schema e $ref;
  3. classificar uma mudança de contrato como compatível ou como quebra, e decidir quando ela exige nova versão;
  4. configurar o Springdoc 3 e documentar controllers e DTOs com @Tag, @Operation, @ApiResponse, @Parameter e @Schema;
  5. documentar cada status real de uma rota, com os erros em ProblemDetail, o esquema bearerAuth e os grupos de documentação.

2. O que é um contrato de API ↑ conteúdo

Um contrato de API é a descrição precisa de tudo que o cliente pode pedir e de tudo que o servidor promete devolver. Quem consome a API programa contra o contrato, e não contra o código interno. A Semana 01 apresentou essa separação entre interface e implementação; agora a interface ganha forma de documento.

O que o contrato fixa

Rotas e métodos HTTP; parâmetros e corpos de entrada; formato das respostas; códigos de status e formato dos erros; como se autenticar.

Por que escrever

Front-end e back-end trabalham em paralelo; quem consome não precisa adivinhar; ferramentas leem o documento e geram testes, clientes e telas de teste.

Um exemplo fora do ServiceHub: o aplicativo de um banco mostra o saldo porque o contrato diz que GET /contas/{id}/saldo devolve um número no campo valor, e 404 quando a conta não existe. Se o servidor renomear o campo para saldo, o aplicativo quebra, mesmo sem nenhum erro de compilação. Contrato é promessa: quem muda o que foi prometido quebra quem confiou nele.

Confusão comum

Achar que documentação de API é só para gente ler. Hoje o documento também é lido por máquinas: geradores de código, simuladores e testes automatizados dependem de que ele esteja certo.

3. Design-first e code-first ↑ conteúdo

Há duas formas de chegar ao documento. A diferença está em quem nasce primeiro e, por isso, em quem é a fonte da verdade.

AspectoDesign-firstCode-first
OrdemEscreve o documento OpenAPI, depois implementa.Implementa, e uma biblioteca gera o documento.
Fonte da verdadeO arquivo YAML ou JSON.O código anotado.
VantagemConsumidores revisam e começam antes de o código existir.O documento acompanha o código a cada mudança.
RiscoO código divergir do documento sem ninguém notar.Contrato feito às pressas, refletindo detalhes internos.
Quando usarAPI pública, vários times consumindo.Time único, contrato estável, boa cobertura de testes.

Não existe vencedor absoluto: é uma decisão de arquitetura, boa candidata a um registro de decisão (ADR). No ServiceHub as duas se encontram. O Mapa de Construção define o contrato antes do código (design-first), e o Springdoc gera o documento a partir do código (code-first). Testes provam que os dois batem.

Armadilha

Dizer "usamos code-first" quando, na verdade, não houve contrato nenhum antes do código, só código. Code-first ainda exige decidir o contrato; a diferença é onde ele é escrito.

4. OpenAPI, Swagger e Springdoc ↑ conteúdo

Os nomes se misturam em tutoriais. Cada um designa uma coisa diferente:

NomeO que éNo ServiceHub
OpenAPI SpecificationPadrão aberto, em JSON ou YAML, que descreve APIs HTTP. É mantido pela OpenAPI Initiative, ligada à Linux Foundation.O documento em /api-docs/v1
Swagger UIPágina web que lê a especificação, lista as rotas e envia requisições pelo botão Try it out.Aberta em /docs
Springdoc OpenAPIBiblioteca que gera a especificação a partir dos controllers Spring.springdoc-openapi-starter-webmvc-ui 3.0.x
SpringfoxBiblioteca antiga com o mesmo objetivo, sem manutenção.Não use.

"Swagger" era o nome antigo da especificação. Quando ela foi doada à OpenAPI Initiative, passou a se chamar OpenAPI, e "Swagger" ficou como nome das ferramentas (Swagger UI, Swagger Editor).

5. A estrutura de um documento ↑ conteúdo

Um documento OpenAPI é um único arquivo JSON ou YAML. A raiz declara, no campo openapi, a versão da especificação usada (por exemplo, 3.0.3 ou 3.1.0). Abaixo dela ficam as partes principais:

PartePara que serve
infoTítulo, descrição, versão do contrato e contato.
serversEndereços base onde a API roda: local, homologação, produção.
pathsCada rota, como /livros/{id}. É o coração do documento.
operationsDentro de cada rota, um objeto por método (get, post…), com parameters, requestBody e responses.
componentsPeças reutilizáveis: schemas, responses, parameters, examples e securitySchemes.
securityCampo opcional na raiz que aplica um esquema de segurança a todas as operações.

Um exemplo genérico em YAML

Uma biblioteca, fora do ServiceHub, para separar o padrão da ferramenta. Em YAML, a indentação aninha os campos e o hífen abre um item de lista; JSON e YAML são equivalentes.

openapi: 3.0.3
info:
  title: Biblioteca API
  version: 1.2.0
servers:
  - url: https://api.biblioteca.exemplo/v1
paths:
  /livros/{id}:
    get:
      summary: Busca um livro pelo id
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: integer, format: int64 }
components:
  schemas:
    Livro:
      type: object
      required: [titulo, isbn]
      properties:
        id:       { type: integer, format: int64 }
        titulo:   { type: string, maxLength: 200 }
        situacao: { type: string, enum: [DISPONIVEL, EMPRESTADO] }
  securitySchemes:
    bearerAuth: { type: http, scheme: bearer, bearerFormat: JWT }
  • openapi é a versão do padrão; info.version é a versão do seu contrato. A diferença costuma cair em prova.
  • {id} na rota exige um parâmetro in: path obrigatório. Outros lugares de parâmetro: query, header e cookie.
  • securitySchemes só declara o mecanismo de autenticação; cada operação (ou o campo raiz security) diz se o exige. Declarar não protege nada: quem protege é o servidor, no ServiceHub o Spring Security.

6. JSON Schema: descrevendo dados ↑ conteúdo

Os schemas do OpenAPI usam o vocabulário do JSON Schema: palavras-chave que dizem que tipo um valor tem e que regras precisa cumprir. A versão 3.1 do OpenAPI se alinhou por completo ao JSON Schema; a 3.0 usa um subconjunto dele. As palavras básicas são as mesmas nas duas:

Palavra-chaveSignificadoDe onde vem no Java (Springdoc)
typestring, integer, number, boolean, array, objectTipo do campo no DTO
requiredCampos que não podem faltar@NotNull, @NotBlank
formatRefina o tipo: int64, date-time, email, uuidLong, LocalDateTime, UUID
enumConjunto fechado de valores aceitosUm enum Java, como ServiceCategory
minLength, maxLengthLimites de tamanho de texto@Size(min, max)
minimum, maximumLimites numéricos@Min, @Max, @DecimalMin

O ponto importante: a Bean Validation da Semana 04 não é só validação em tempo de execução. O Springdoc lê essas anotações e as escreve no contrato. Um @Size(max = 150) no título vira maxLength: 150 no schema, sem você escrever de novo.

Para lembrar

format é uma dica para quem consome. Quem garante a regra continua sendo a validação no servidor: um cliente pode ignorar o documento e mandar qualquer coisa.

7. Reuso com $ref ↑ conteúdo

$ref é uma referência: no lugar do conteúdo, um caminho até onde ele está definido. O caminho segue o padrão JSON Pointer: #/ é a raiz do próprio documento, e cada / desce um nível.

paths:
  /livros/{id}:
    get:
      responses:
        '200':
          description: Livro encontrado
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Livro'
        '404':
          $ref: '#/components/responses/NaoEncontrado'

Mudou Livro? Todas as rotas que apontam para ele mudam juntas. É o princípio de não repetir (DRY) aplicado ao contrato. O $ref também pode apontar para outro arquivo, o que ajuda em contratos grandes escritos à mão. No code-first, o Springdoc gera os $ref sozinho: cada DTO aparece uma vez em components/schemas, e as rotas só apontam para ele.

8. Exemplos e descrições ↑ conteúdo

Um contrato que só tem tipos responde "o quê", mas não "por quê" nem "quando". Três elementos fazem o contrato se explicar:

  • summary e description: summary é a linha curta da lista de rotas; description explica regras, quem pode chamar e efeitos colaterais.
  • example: um valor realista por campo. Ferramentas usam o exemplo para pré-preencher o Try it out, montar testes e simular respostas.
  • Erros descritos: cada status diz quando ocorre. "409 se o e-mail já existe", e não só "Conflict".
CampoDescrição fracaDescrição útil
isbnstring · "ISBN"13 dígitos, sem hífens · exemplo 9788550808161
pricenumber · "Preço"Preço em reais, maior que zero, duas casas · exemplo 150.00
Erro comum em código gerado por IA

example = "string", descrições que só repetem o nome do campo e respostas de erro sem dizer quando acontecem. Regra prática: uma boa descrição responde o que o tipo sozinho não responde.

9. Versionamento e compatibilidade ↑ conteúdo

Há duas versões diferentes num contrato, e confundi-las é comum.

info.version: 1.2.0

Versão do documento. Muda a cada alteração do contrato e costuma seguir o versionamento semântico, MAJOR.MINOR.PATCH: MAJOR quebra clientes, MINOR acrescenta sem quebrar, PATCH corrige texto ou exemplo.

/api/v1/…

Versão na URL. Muda só quando há quebra. A v1 continua no ar enquanto os clientes migram para a v2. Alternativas: cabeçalho ou tipo de mídia; a URL é a mais simples de ver e de testar.

Por isso todas as rotas do ServiceHub começam em /api/v1: a porta para uma v2 fica aberta desde o primeiro dia. Mas criar /api/v2 para qualquer ajuste multiplica código a manter. A pergunta certa é: a mudança quebra quem já usa?

Mudança no contratoEfeito em quem já consome
Nova rota ou novo parâmetro opcionalCompatível: ninguém é obrigado a usar.
Novo campo na respostaCompatível, se o cliente ignora campos desconhecidos.
Remover ou renomear campo da respostaQuebra: o cliente lê um campo que sumiu.
Campo opcional da entrada vira obrigatórioQuebra: requisições antigas passam a dar 400.
Trocar o tipo de um campo (número para texto)Quebra: a leitura falha no cliente.
Trocar o status de sucesso (200 para 201)Quebra clientes que testam o código exato.

A regra que resume a tabela é uma leitura do princípio da robustez: na entrada, seja tolerante; na saída, nunca retire o que já prometeu. Um caso sutil: acrescentar um valor novo a um enum da resposta pode quebrar clientes que tratam só os valores conhecidos.

10. O contrato a serviço de ferramentas ↑ conteúdo

Um documento legível por máquina gera trabalho pronto. Três usos aparecem em qualquer equipe que leva o contrato a sério (aqui, só o conceito; não vamos gerar clientes na disciplina):

  • Cliente gerado: um gerador, como o OpenAPI Generator, lê o documento e produz classes e métodos tipados em TypeScript, Java, Kotlin e outras linguagens.
  • Servidor simulado (mock): responde com os exemplos do contrato. O front-end trabalha antes de o back-end existir.
  • Teste de contrato: confere se a implementação responde como o contrato promete, com os mesmos status, campos e tipos, e falha antes que o cliente descubra. Na variante guiada pelo consumidor, cada cliente declara o que espera e o servidor prova que atende.

Ferramentas de apoio consomem o mesmo arquivo: o Swagger UI lista as rotas e envia requisições; o Swagger Editor valida o YAML com prévia ao lado, útil no design-first; o Postman, cliente HTTP com coleções, variáveis de ambiente e testes, importa um documento OpenAPI e cria a coleção. É a vantagem de um padrão aberto.

11. As anotações do Springdoc ↑ conteúdo

Só com a dependência no pom.xml, o Springdoc já documenta todas as rotas, mas mal: sem descrições, com status adivinhados e sem exemplos. As anotações transformam esse rascunho em contrato. Cada uma responde a uma pergunta de quem consome:

PerguntaAnotaçãoOnde
Em que grupo está?@Tag(name, description)Na classe do controller, uma por recurso.
O que a rota faz?@Operation(summary, description)No método.
O que pode voltar?@ApiResponses / @ApiResponseNo método, um por status.
O que eu envio?@Parameter, @ParameterObject, @SchemaNos parâmetros e nos campos dos DTOs.

Um controller genérico de livros, documentado (resumido):

@RestController
@RequestMapping("/livros")
@Tag(name = "Livros", description = "Acervo da biblioteca")
public class LivroController {

  @Operation(summary = "Buscar livro por id",
      description = "Público. Livro retirado do acervo responde 404.")
  @ApiResponses({
    @ApiResponse(responseCode = "200", description = "Livro encontrado"),
    @ApiResponse(responseCode = "404", description = "Livro não existe",
      content = @Content(mediaType = "application/problem+json",
        schema = @Schema(implementation = ProblemDetail.class),
        examples = @ExampleObject(name = "nao-encontrado", value = """
          {"type": "urn:biblioteca:problem:not-found",
           "title": "Recurso não encontrado", "status": 404,
           "detail": "Livro não encontrado: 99", "instance": "/livros/99"}""")))
  })
  @GetMapping("/{id}")
  public LivroResponse buscar(
      @Parameter(description = "Id do livro", example = "42") @PathVariable Long id) { ... }
}
  • summary é verbo e objeto, curto; description diz quem pode chamar e o que a rota decide sozinha.
  • Cada @ApiResponse de erro aponta para ProblemDetail, com o tipo de mídia application/problem+json. O @ExampleObject mostra no Swagger UI um corpo de erro realista.
  • @ParameterObject, usado num Pageable, abre o objeto em page, size e sort, um campo cada no formulário.
  • @Schema(description, example) num campo de record vira descrição e exemplo do schema; o exemplo pré-preenche o corpo do Try it out.
  • @SecurityRequirements vazio numa operação diz "esta rota é pública", tirando o cadeado que um requisito global de segurança colocaria.
Documente o que existe, nem mais nem menos

Dois erros opostos. Documentar 400, 401, 403, 404, 409 e 500 em toda rota "por garantia" mente sobre o contrato. Inventar uma classe ErrorResponse que não existe no projeto também: o erro real é ProblemDetail. Cada status documentado deve corresponder a uma condição que o código produz ou que o contrato do Mapa exige.

A linha 3.x do Springdoc é a que acompanha o Spring Boot 4; a 2.x, comum em tutoriais, não funciona com ele. Os caminhos padrão seriam /v3/api-docs e /swagger-ui.html; o ServiceHub usa /docs e /api-docs, como o Mapa pede.

O bean OpenAPI: cabeçalho e segurança

config/OpenApiConfig.java (resumido; a descrição completa e a licença foram cortadas):

@Bean
public OpenAPI servicehubOpenAPI(ObjectProvider<BuildProperties> buildProperties) {
    BuildProperties props = buildProperties.getIfAvailable();
    return new OpenAPI()
        .info(new Info().title("ServiceHub API")
            .version(props != null ? props.getVersion() : "dev"))
        .servers(List.of(
            new Server().url("http://localhost:8080").description("Execução local"),
            new Server().url("http://localhost:8090").description("Docker Compose")))
        .components(new Components().addSecuritySchemes(BEARER, new SecurityScheme()
            .type(SecurityScheme.Type.HTTP).scheme("bearer").bearerFormat("JWT")))
        .addSecurityItem(new SecurityRequirement().addList(BEARER));
}

O addSecurityItem global marca todas as rotas como protegidas; as públicas (cadastro, login, catálogo) declaram @SecurityRequirements vazio. Os servers viram o seletor de ambiente do Try it out. Um segundo bean, securityResponsesCustomizer (um OpenApiCustomizer), percorre as operações e acrescenta 401 e 403, com schema ProblemDetail, a toda rota que não é pública. Assim esses dois status não precisam ser repetidos em cada controller.

Grupos v1 e public

Dois beans GroupedOpenApi recortam a documentação. O grupo v1 (.group("v1").pathsToMatch("/api/v1/**")) traz a API inteira; o grupo public reúne o que um visitante sem conta usa: cadastro, login, catálogo, avaliações e /info, excluindo /api/v1/services/*/status. Os dois recebem o securityResponsesCustomizer. Cada grupo tem a sua especificação (/api-docs/v1 e /api-docs/public), e um seletor no topo do /docs troca entre eles.

Um controller documentado

controller/ServiceOfferingController.java (resumido; PROBLEM vale "application/problem+json"):

@Tag(name = "Serviços",
     description = "Catálogo de serviços oferecidos pelos prestadores da plataforma")
public class ServiceOfferingController {

    @Operation(summary = "Cadastrar serviço",

            + "criado e o header Location.")

A description conta uma regra de segurança (o prestador vem do token): quem consome precisa saber disso para montar o corpo certo. Na listagem, cada filtro tem @Parameter(description, example), o Pageable recebe @ParameterObject, e a @Operation diz em texto o tamanho padrão (20), o máximo (100) e os campos aceitos em sort, porque o teto não aparece sozinho na especificação.

13. Construindo com IA ↑ conteúdo

Documentação é onde a IA mais "inventa": ela lista status plausíveis em vez dos reais. Por isso a especificação vem do Mapa e do código, nunca do assistente.

  • Especificar: escreva a tabela de status por rota a partir da seção 6.3 do Mapa.
  • Gerar: peça um plano que ligue cada status a uma condição do código; só depois as anotações.
  • Revisar: cada status bate com uma exceção do código ou com o Mapa? Nenhum 500?
  • Provar: um corpo inválido no /docs devolve o 400 documentado.

Prompt fraco e prompt bom

Fraco

adiciona swagger no projeto e documenta tudo

Vêm Springfox, 500 em toda rota e uma ErrorResponse inventada.

Bom

Fixa versão e caminhos, entrega a tabela de status, exige ProblemDetail com exemplo, pede plano e um aceite verificável. Está logo abaixo.

O prompt desta semana

Ponto de partida: o projeto da Semana 04, com o CRUD de serviços e o GlobalExceptionHandler.

Contexto: API ServiceHub, Java 21, Spring Boot 4.1, pacote
com.servicehub. Já existem ServiceOfferingController (CRUD em
/api/v1/services), DTOs em record e GlobalExceptionHandler com
ProblemDetail (RFC 9457), type urn:servicehub:problem:<tipo>.
O contrato é a seção 6.3 do Mapa (anexo).

Objetivo: documentar o ServiceOfferingController no OpenAPI.

Status por rota (seção 6.3 do Mapa):
- POST   /services        201 · 400 · 401 · 403
- GET    /services        200 · 400 (filtro ou sort inválido)
- GET    /services/{id}   200 · 404
- PUT    /services/{id}   200 · 400 · 401 · 403 · 404 · 409
- DELETE /services/{id}   204 · 401 · 403 · 404 · 409

Restrições:
- springdoc-openapi-starter-webmvc-ui 3.0.x. NÃO use Springfox nem
  springdoc 2.x. Caminhos: springdoc.swagger-ui.path=/docs e
  springdoc.api-docs.path=/api-docs.
- @Tag na classe; @Operation com summary e description em cada rota.
- Cada erro: @ApiResponse com @Content(mediaType =
  "application/problem+json", schema = @Schema(implementation =
  ProblemDetail.class)) e um @ExampleObject com o JSON do Mapa
  (type, title, status, detail, instance).
- NUNCA documente 500. NÃO crie classe ErrorResponse.
- 401 e 403 de token: declare o esquema bearerAuth no bean OpenAPI
  e um OpenApiCustomizer que os acrescenta às rotas protegidas. As
  rotas GET públicas recebem @SecurityRequirements vazio.
- Listagem: @Parameter com exemplo em cada filtro e @ParameterObject
  no Pageable; a description informa padrão 20, máximo 100 e os
  campos aceitos em sort.
- @Schema com exemplo do domínio nos DTOs (nunca "string").
- Não altere o comportamento de nenhuma rota.

Antes do código, mostre um plano: uma tabela com rota, status,
condição que o produz (exceção ou regra) e type. Marque como
"pendente" o status que o Mapa exige e o código ainda não produz
(ex.: 401/403 antes da Semana 08; 409 antes das ordens).

Critério de aceite: o Swagger em /docs mostra, em cada rota, cada
status da tabela com o schema ProblemDetail e o exemplo; nenhuma
rota mostra 500; /api-docs/v1 contém "bearerAuth".

O que a IA costuma errar nesta etapa

  • Springfox ou springdoc 2.x, que não funcionam com o Boot 4; caminhos padrão /v3/api-docs e /swagger-ui.html.
  • Inventar ErrorResponse em vez de usar ProblemDetail.
  • Listar "400 a 500 em toda rota por garantia", inclusive status que a rota não devolve.
  • Esquecer @SecurityRequirements nas rotas públicas, que ficam com cadeado no /docs.

Checklist de revisão

14. Glossário ↑ conteúdo

Contrato de API
Descrição precisa do que o cliente pode pedir e do que o servidor promete devolver.
OpenAPI
Padrão aberto, em JSON ou YAML, para descrever APIs HTTP.
Swagger UI
Página que lê um documento OpenAPI, lista as rotas e permite testá-las.
Springdoc
Biblioteca que gera o documento OpenAPI a partir de controllers Spring.
Design-first
Abordagem em que o documento é escrito antes do código.
Code-first
Abordagem em que o documento é gerado a partir do código anotado.
Path / operation
Uma rota do documento e, dentro dela, o objeto de cada método HTTP.
Components
Seção de peças reutilizáveis: schemas, respostas, parâmetros, exemplos, segurança.
Schema
Descrição da forma de um dado, com o vocabulário do JSON Schema.
$ref
Referência a uma definição feita em outro ponto do documento.
securityScheme
Declaração de um mecanismo de autenticação, como bearer JWT.
Versionamento semântico
Esquema MAJOR.MINOR.PATCH: quebra, acréscimo compatível, correção.
Mudança que quebra
Alteração que faz um cliente existente parar de funcionar.
Teste de contrato
Teste que confere se a implementação responde como o contrato promete.
